# Sprint 1 — Frame Capture + Timestamp Convention

**Status:** In progress (started 2026-09-21). Pi steps blocked until SSH key auth works, see Progress log.
**Required for Phase 1:** Yes
**Depends on:** nothing
**Effort:** M–L (the measurement work is what makes this one large)

## Goal

Capture individual IMX219 frames on the Pi 3B at a fixed 30 fps trigger rate. Each frame is written as its own file, and every capture gets one row in a CSV ledger (filename + timestamp). Measure and document the frame rate the hardware actually achieves. Fix the timestamp convention that every later stream inherits.

## Scope (from the brief)

**In:**
- Fixed-interval capture trigger targeting 30 fps
- One file per frame, with a naming convention
- CSV ledger: one row per captured frame

**Out:**
- Video libraries, `cv2.VideoWriter`, any codec or container output
- CAN/GPS/IMU correlation
- Any frame processing, inference, or compression choices beyond what saving the image needs
- Cloud upload

## Decisions this sprint makes (with my recommendation)

| Decision | Recommendation | Why |
|---|---|---|
| Language / capture stack | Python 3 + `picamera2` (libcamera) first; drop to C++ only if the spike shows Python can't keep up | Simplest path. The spike will show whether the encode/write path is the bottleneck. |
| Trigger mechanism | Let the sensor free-run at 30 fps (fixed frame duration) and take each frame's timestamp from the sensor, not from a software timer | A software timer adds jitter on a loaded Pi 3B. The sensor timestamp is the truest capture time. |
| Timestamp clock | Integer nanoseconds from a monotonic clock, plus a wall-clock anchor written once per session in a manifest | The Pi has no RTC, so wall time can jump when NTP or GPS sets it. Monotonic time never does. The anchor lets Phase 2 convert to UTC. |
| CSV columns | `seq, filename, timestamp_ns` | The brief requires filename + timestamp. I'm adding `seq` (a per-frame counter from the capture pipeline) so dropped frames show up as gaps instead of being invisible. **Approved by you 2026-09-21.** |
| Resolution / JPEG quality | Chosen from spike results, not up front. **You set no minimum resolution (2026-09-21)**, so the spike measures all modes and you pick from the numbers | 30 fps at full resolution will probably exceed what the 3B's CPU and storage can sustain. The spike finds the best operating point. |
| File layout | `sessions/<session_id>/frames/<seq>.jpg`, with subfolders every N thousand files if the spike shows directory size hurts | Predictable, sortable, and tolerable to walk. |

## Risks

- **The Pi 3B can't do 30 fps at a useful resolution with JPEG.** Likely enough that the spike exists. The outcome is a documented, measured number, which the brief explicitly expects.
- **SD card write speed is the likely bottleneck** and may force a lower resolution or rate than the sensor and CPU could otherwise do. Sustained small-file writes are also hard on SD cards (wear, and latency spikes when the card garbage-collects). The SSD re-run in task F is the way out. Note for your purchase: the 3B only has USB 2.0, which caps real throughput at roughly 30–40 MB/s and is shared with Ethernet, so any decent SSD (or fast USB flash drive) will do. A fast NVMe drive would be wasted on this board.
- **Thermal throttling** in a hot car changes the numbers over a long session. The 10-minute runs record throttle flags, and I'd suggest one longer run too.
- **Python overhead** in the encode/write path. Mitigated by the worker-pool and C++ fallback options above.
